# ZW810 单节点专家补载与控制开销实验方案

## 1. 目的与当前汇报口径

本实验使用可访问 PPU ZW810 的另一台电脑，测量单节点内将专家从主机 DDR 换入加速器设备内存的速度，以及 CPU 参与需求检查与补载调度时造成的额外等待。优先使用一张 ZW810 即可开始，无需多节点网络，也无需完整大模型或新增专利硬件。

当前用于汇报的暂估如下。所有数值均为工程猜测，不是 ZW810 测量结论。

| 项目 | 单层、每步 | 两层阶段、每步 | 性质 |
|---|---:|---:|---|
| CPU 控制闭环时间 | 15 μs | 30 μs | 暂取中间情景 |
| 专利模块控制时间 | 2 μs | 4 μs | 沿用设计预算，尚未实现测量 |
| 控制时间差额 | 13 μs | 26 μs | 假设差额全部暴露在执行路径上 |

软件控制时间另取两层合计 10、30、60 μs 做敏感性分析。它们是情景点，不是统计置信区间或硬件上下界。按当前服务器模拟阶段时间 2.354196488 ms，26 μs 差额对应约 1.10% 的硬件额外阶段能力收益。若差额被专家计算隐藏，实际时间收益更低，可能接近零。

这里的 30 μs 包含每步需求检查及按实际缺失频率摊销的补载调度，不能在每次专家缺失时重复加收整个 30 μs。实验完成后应用测量值替代这一合并猜测。

## 2. 测量结果与现有 PPT 的关系

当前 PPT 是服务器部署模拟，ZW810 是用于验证局部机制的实验平台。两种口径分别保存。

| 测试目标 | 应更新什么 | 保留什么 |
|---|---|---|
| 验证 CPU 控制闭环在 ZW810 上要多久 | 单列 ZW810 控制测量值及分布 | 现有服务器模拟的计算时间、网络带宽及覆盖率假设 |
| 评估 ZW810 单节点的完整局部收益 | 重新测量 ZW810 专家计算、Gate、主机到设备复制、检查及调度时间 | 工作负载定义与公平对比规则 |
| 预测服务器新增硬件收益 | 使用明确的平台映射与参数扫描，标注哪些参数来自 ZW810 | 不将 ZW810 的软件闭环直接称为服务器实测值 |

因此，只做局部控制实验，不要求重算 PPT 全部计算时间；若报告“ZW810 实测端到端收益”，则必须使用同平台、同精度、同形状的计算和搬运数据。现有 PPT 中 0.944 ms 专家 GEMM、0.100 ms Gate，以及 2.160 ms 共同成本，均不能直接作为 ZW810 实测成本。

ZW810 没有本专利新增模块。实验能测软件控制路径，并建立可去除控制等待的参考值；硬件的 2 μs/层仍是设计预算。不得将已有设备算子模拟的路径直接等同于新增电路的真实实现。

## 3. 实验问题的简化抽象

只考虑本节点负责的一个或少数完整 MoE 层。每层分别维护需求和驻留状态，不设置跨层唯一的“当前活跃层”。最小测试可先串行测一层，再测两层阶段。

- 全部待换入专家在本机 DDR 中已有副本，不访问磁盘、Flash 或远程网络。
- 设备内存中预分配专家槽，固定槽数，不在计时区间内分配或释放权重内存。
- 当前专家需求由设备端生成，CPU 路径必须取得该轮结果后才能作出决定。不得将提前放在 CPU 的需求序列当作真实的 CPU 闭环。
- 每步对本节点请求的专家需求取并集，与驻留集合比较。批内请求的检查合并处理，避免为每个 token 单独执行一次设备—CPU同步。
- 命中时使用已驻留专家。缺失时更新空闲槽，提交权重复制，等待正确的就绪事件，再执行依赖该专家的计算。
- 已驻留专家可以先执行；最终输出仅使用本轮真实路由选中的专家及本轮权重，丢弃旧选择带来的多余结果。

本实验不验证跨节点 All-to-All 降幅，也不验证 Prefill 专家亲和性在大模型 Top-8 上的预测质量；这两个指标独立于局部补载测试。

## 4. 开始前在测试电脑确认的条件

### 4.1 记录环境

记录 ZW810 设备型号、可用设备内存及内存类型、卡数、CPU 型号、操作系统、内核、主机 DDR 配置、设备与 CPU 的 NUMA 关系、实际 PCIe 代际/链路宽度、驱动、固件、运行时、框架及插件版本。记录 CPU 线程亲和性、频率策略和是否有其他作业。

先使用测试电脑已经跑通的 ZW810 初始化、张量分配与矩阵乘法示例。现有仓库材料没有提供足以确认的 ZW810 原生同步、事件和异步复制 API，本方案不假设 `torch.cuda`、`torch.ppu` 或某一插件名称可直接使用。

### 4.2 建立运行时能力表

| 功能 | 需要核实的问题 | 无该能力时的处理 |
|---|---|---|
| 设备同步 | 是否能确认指定队列或整个设备已完成 | 用平台支持的明确完成机制，不用固定 sleep |
| 设备事件计时 | 是否支持事件、事件精度及跨队列依赖 | 使用 CPU 墙钟加完成同步，标明包含同步成本 |
| pinned 主机内存 | 分配方式及复制时是否实际使用 pinned 缓冲 | 使用普通内存另列结果，不混称 pinned 速度 |
| 主机到设备复制 | 是否支持预分配目标的原地复制 | 若仅支持新建张量，单独披露分配成本 |
| 异步复制与多队列 | 返回是否仅代表提交、计算能否真正并行 | 只报告串行结果，重叠项填“不支持/未验证” |
| 图重放或持久任务 | 是否能预置固定动作、设备端触发 | 不伪造无 CPU 调度路径，保留为模型参考 |
| 性能时间线 | 是否能区分计算、复制、CPU 提交与等待 | 保留墙钟闭环为主结果，不能可靠拆分的字段留空 |

设备内存只有确认属于 HBM 时才写作 HBM；其余统一记“设备内存”。CPU 与设备的绝对时间戳不能直接相减，除非工具明确支持时钟对齐。

## 5. 工作负载与数据准备

### 5.1 专家大小与缓冲

主复制对象采用 44,050,944 B，约 42.01 MiB，对齐当前 PPT 的 FP8 专家字节量。该对象可用原始字节缓冲复制，不要求 ZW810 支持 FP8 计算。另扫 1、8、16、84 MiB，以观察固定提交开销和大块带宽段。

复制测试与实际 GEMM 的精度分开记录：如 ZW810 只使用 BF16/FP16，三矩阵专家的原始权重约 84 MiB，不能将 42.01 MiB 的复制时间配到 84 MiB 的真实计算实现中。FP8 反量化、格式转换或数据重排如存在，单列耗时。

主机源缓冲与设备目标槽全部预分配并预触碰。复制计时前初始化一次数据；计时区间内不生成随机数、不读文件、不执行内存分配。完成后抽样校验内容，所有用来 DMA 的缓冲在复制完成前保持有效且不改写。

### 5.2 路由摘要与驻留集合

- 专家池 E=128，Top-8，每层先有 10 个驻留专家，并预留 2 个更新槽。
- 首测请求数 B=256，再测 B=2048。这里 B 表示该被测域处理的请求数，不自动解释为原八卡节点每卡请求数。
- 每请求 128-bit 需求位图为 16 B，B=2048 时每层 32 KiB。另测在设备上先归并为一个 16 B 节点需求位图再回传 CPU 的实现。
- 对比“原始请求 ID 回传 CPU 后归并”和“设备先归并、CPU 只检查摘要”两种可行软件路径。后者若更优，应作为主要软件基线，避免将可优化的软件低效当作专利收益。
- CPU 归并采用紧凑数组/位运算实现，避免 Python 对象集合反复分配；若仅能运行 Python 原型，单列为原型结果。

使用固定随机种子生成可重复路由。主需求集合只在少量专家中往复，不能每次切换都制造新专家。至少测试：全命中；第 32 步和第 48 步各新增一个专家；同一步新增两个专家；每步缺失一个专家。加入 A→B→A 的回访，验证目录与缓存复用。

先用 64 步窗口对齐 PPT，再用 1024 步窗口验证稳态。初始装入、稳态补载分别计费，报告含初始成本与不含初始成本的结果。缺失事件数、专家数及描述符数分别统计，不能互相替代。

## 6. 具体实验

### 实验 A：计时与提交基准

测量墙钟读取开销、空队列完成同步、最小设备任务，以及设备已完成时的小摘要回传。每项独立记录，作为计时解释依据。正式闭环测量保留其实际需要的同步，不机械地将空同步耗时从所有结果里扣除。

目的：确认计时分辨率、运行时固定开销，并区分 Python/框架包装耗时与底层提交耗时。平台有原生接口时，可补充原生实现；两种实现分栏报告。

### 实验 B：纯 DDR→设备内存复制

1. 固定同一个预分配目标槽，分别使用普通与 pinned 主机缓冲。
2. 扫描复制字节量，分别记录 API 返回所需 CPU 时间和数据实际可供设备计算使用的完成时间。
3. 如支持事件，记录设备复制时间；如不支持，使用“提交前墙钟—完成同步后墙钟”，明确它是闭环时间。
4. 测一个、两个专家分别提交与合并提交的差异。将专家布局准备、打包成本另列，不能免费假设连续存储。
5. 只有可证明无隐式串行时才报告异步带宽；`non_blocking` 一类参数本身不能证明发生了重叠。

报告有效带宽 `bytes / completion_seconds`，使用十进制 GB/s；复制大小另保留 B 与 MiB。可对大块数据拟合 `T(S)≈a+S/B`，其中 a 是整体固定开销估计，不能未经拆分就全部称为 CPU 调度开销。

### 实验 C：每步需求检查的 CPU 闭环

构造两条路径，设备产生完全相同的路由结果，执行同样的下游小计算。

- CPU 动态路径：设备生成本轮需求摘要，CPU 取得可读结果，完成并集/差集与槽位查询，提交下一动作，设备执行依赖该决定的消费者任务。
- 预先确定路径：给定相同最终决定，省去 CPU 读取和判断，执行同样的摘要生成及消费者任务。固定序列提前提交、图重放或持久任务仅在平台支持时使用，并完整披露 CPU 是否仍参与逐步提交。

先运行全命中场景，避免大权重复制掩盖控制开销。比较两条完整路径的总时间差，优先使用成对交替测量。预先确定路径是可消除动态控制的参考，不是新增硬件的实测。

无法构造有效参考时，直接报告 CPU 闭环的绝对耗时及可观测子项，不编造硬件差值。

### 实验 D：缺失时补载与后续计算就绪

在实验 C 中注入明确的专家缺失，完整执行：需求可读、目录查询、选槽、描述符准备、复制提交、复制完成、目录有效标记、依赖该专家的首次 GEMM。

预先确定路径使用同一组源数据、目标槽、复制字节量和消费者 GEMM。缺失控制参考差值定义为两条路径成对测得的差异，不能简单把“总闭环减纯复制”当作全部可节省控制时间，因为它还可能包含队列、同步及消费者启动成本。

检查无覆盖在途专家、无未完成复制被提前使用、无错误逻辑—物理映射；涉及推测执行时，真实路由确定后才提交有效结果。

### 实验 E：加入并行计算，测真正暴露的控制成本

先使用时长约 0、50、200、500、1000 μs 的实际设备 GEMM 作为并行计算，具体持续时间以 ZW810 校准结果为准，不用主机 sleep 模拟。

对命中与缺失路径分别测：

1. 串行需求检查/补载后计算。
2. 先执行已驻留专家，同时进行需求检查及允许的复制，最后等待必要的依赖并提交结果。
3. 相同计算、复制与最终结果的预先确定路径。

主要指标为在并行条件下，CPU 动态路径相对参考路径的阶段时间差。单独报告控制路径总时长与最终暴露时间，不能将总时长直接全部加进阶段收益。

重叠必须由时间线或总时间对照验证。比较 `T计算`、`T复制`、`T并行`，并行理想值 `max(T计算,T复制)` 仅作参考；内存带宽争用可能使实际执行偏离理想值。不要用人为强制串行的软件实现证明硬件优越。

### 实验 F：ZW810 局部完整前向（第二优先级）

仅在需要报告 ZW810 平台完整效果时执行。先单层，再在资源允许时执行两层。独立测真实 Gate、摘要/位图生成、专家 GEMM、本地复制、额外执行、合并与控制时间。

真实专家计算按 `d=7168,m=2048` 尝试，按支持的精度运行三矩阵专家；每个专家的 token 数扫 1、32、128、256，不将节点 B=2048 直接赋给每个专家。内存不足时缩小 d、m，并把形状变化写入配置；结果不直接冒充原大模型规模。

比较驻留路径与带主机 DDR 专家槽的路径，必要时加入相同缓存策略的 CPU 动态/预先确定控制对照。单卡实验无法验证八卡共享 DDR 带宽、节点内互联或跨节点 EP 收益。

## 7. 计时方法与正确性

- 预热不少于 100 次，或直至最近两批延迟稳定；预热与首次编译、上下文初始化单独记录。
- 命中短路径每组至少 1000 次；大块补载每组至少 100 次。至少运行 5 轮，交替或随机安排对照顺序。
- 报告各轮均值以及 p50、p95、p99。总收益使用可加总的均值与实测总时间；不得把多个子项的中位数相加，当作完整闭环的中位数。
- 稳态吞吐在计时区间首尾同步，中间仅保留算法依赖所需同步；单次闭环实验另外运行，不能混用两种口径。
- wall-clock 使用单调高精度时钟。CPU 提交时间不能代替设备完成时间，设备事件也未必包含主机等待。
- profiler 只用于少量路径归因，最终时延关闭 profiler 后复测。不要在计时区间内打印、保存文件或拷回完整计算结果。
- 验证每种路径最终选中的专家一致、权重正确、输出在对应精度容差内一致，记录多余执行量。错误路径不进入收益统计。
- 先测空闲主机，再测存在可控 CPU 工作负载的情况。两者分栏，不能只选系统忙时的数据作为普通软件开销。

## 8. 结果计算与回填方式

### 8.1 分清三种时间

- `C_cpu`：CPU 动态控制闭环的总耗时。
- `C_exposed`：在允许并行计算后，动态控制相对有效参考所增加的阶段等待时间。
- `C_hw_budget`：专利模块对应功能的设计预算，当前两层合计 4 μs，非实测。

对于命中和缺失，应分别统计暴露时间，再按事件频率合并。可写为 `E[C_exposed]=(1-q)*C_hit_exposed+q*C_miss_exposed`，其中 q 为每步是否出现缺失的概率；同一步存在多次事务时，应使用实际事务明细或直接统计窗口总时间。新增两个专家不能直接推出 q。

硬件暴露时间应由相同调度窗口估算。例如命中路径可用 `max(0,C_cpu-W)` 与 `max(0,C_hw_budget-W)` 比较，W 是可覆盖控制的真实计算窗口。这只是简化近似；缺失路径还含复制和就绪依赖，优先使用实验 E 的完整时间线。

### 8.2 保持现有服务器模拟时

当前 PPT 的硬件方案阶段时间为 2354.196488 μs，已含两层 4 μs 控制预算。若 CPU 控制暴露时间设为 30 μs、硬件 4 μs 均完整暴露，则：

```text
同算法 CPU 方案阶段时间 = 2354.196488 - 4 + 30 = 2380.196488 μs
硬件相对同算法 CPU 方案的能力收益 = 2380.196488 / 2354.196488 - 1 ≈ 1.10%
```

原有相对普通 MoE 的约 10.5% 阶段能力收益已经是当前硬件方案的数值，不再额外叠加 1.10%。该对照用于解释硬件贡献；算法与硬件的百分比不能简单相加。

ZW810 的闭环值只能标为该平台测量；用于服务器估算时，必须注明跨平台借鉴假设。若只拿到总闭环时间，不能直接作为全部暴露时间回填。

### 8.3 报告 ZW810 完整结果时

使用相同测试环境下的两条完整路径总时间直接计算能力比与延迟降幅。所有计算、数据类型、权重字节量与复制时间采用 ZW810 实测。不要将 ZW810 单卡结果与服务器 200 GB/s 节点网络、50 GB/s/卡复制和 NVIDIA profiling 直接拼成一份“实测端到端收益”。

单卡主机到设备带宽只能更新单卡项。八卡节点共享供数上限需要多卡同时复制才能测出；若没有多卡，该字段保留假设，不能用单卡实测带宽乘八宣称已验证。

## 9. 带到另一台电脑后的执行顺序与交付记录

本文件是实验规格，尚未包含与 ZW810 特定 SDK 绑定的可运行脚本。请在测试机先找到已经成功执行的初始化、复制、同步及矩阵乘法示例，将对应 API 填入第 4 节能力表，再实现同一套计时框架。无需先部署完整模型。

最小执行顺序：

1. 环境及能力表；验证一个小张量真实复制完成且内容正确。
2. 实验 A、B：固定提交开销、42.01 MiB 专家复制时间及有效带宽。
3. 实验 C：每步全命中需求检查，识别 CPU 闭环是否已达到几十微秒。
4. 实验 D：缺失一个/两个专家的完整换入时间。
5. 实验 E：加入专家计算，确认这些控制等待实际暴露多少。
6. 需要 ZW810 端到端结论时，再执行实验 F。

建议结果目录：

```text
zw810_expert_loading_results/
  environment.md
  runtime_capabilities.md
  command.txt
  config.json
  samples.csv
  summary.csv
  correctness.json
  timeline/             # 仅少量代表性轨迹
  notes.md
```

`samples.csv` 至少包含 `run_id,experiment,path,layers,requests,expert_bytes,dtype,host_memory_type,miss_events,experts_loaded,copy_descriptors,compute_us,api_submit_us,closed_loop_us,device_copy_us,total_window_us,iterations,correct`。没有可靠测量的字段留空，不填零。

`summary.csv` 按路径、复制大小、内存类型、计算窗口分别汇总均值、p50/p95/p99、有效带宽与成对时间差。保留完整命令、源代码版本、SDK 版本和随机种子。只交换小型结果及配置，不需要上传专家权重或大模型。

最终需要回答四个问题：42.01 MiB 专家实际多久到达设备；CPU 动态判断使控制闭环多长；并行计算后仍暴露多少等待；在同一工作量下，消除这段等待最多能增加多少阶段能力。
