# 面向连续专家路由的跨设备通信状态复用控制器及更新协议

## 摘要

本方案面向多 GPU、NPU 或多芯粒的专家并行推理。在通信控制器中保留每个请求、每一层对应的专家目标、接收队列、返回位置与版本信息。当前真实路由保持相同且记录有效时，新 token 激活沿已有映射发送；路由改变或接收端状态失效时，更新相应记录。

三阶段算法使同一请求在同一层连续多个 token 选择相同专家，允许通信状态跨 token 持续复用。本方案围绕真实路由确认、接收端资源分配、状态增量更新和在途消息正确性形成完整协议，目标是减少低并发解码中的分发控制与元数据开销。

本文将该方向作为优先讨论候选。相关工作基于已有检索，性能为待验证模型，尚未形成完整专利新颖性结论。

## 1. 问题动机与算法依据

### 1.1 专家并行的执行场景

模型的专家分布在不同设备，当前层 Attention 产生激活及路由结果后，源设备将激活发送到目标专家设备；专家计算完成，结果返回原请求的后续执行位置。

低并发 decode 的每条消息较小，通信时延可能受目标解析、元数据组织、队列提交和完成通知影响。跨设备通信仍需承载每个 token 的新激活及输出。

### 1.2 连续路由提供的机会

Attention-Mean Routing 使用注意力输出的局部因果均值选择专家，完整激活继续参与专家计算。项目 M、L 模型的专家切换率约为 5.48%、6.40%。同一请求同一层因而可以连续使用相同专家目标。

该数据来自单请求轨迹。云端还需考虑请求数、专家迁移、负载均衡和队列可用性，因此通信记录的失效率应单独测量。

## 2. 现有方案及相关工作

### 2.1 高效专家通信库

[DeepEP](https://github.com/deepseek-ai/DeepEP)提供专家分发与结果汇合通信，是重要的实现基线。[vLLM 专家并行部署](https://docs.vllm.ai/en/latest/serving/expert_parallel_deployment/)提供面向 decode 的低延迟通信后端。

现有系统通常已复用连接、缓冲区和部分通信资源。本方案需要核实其仍逐轮执行的分发工作，并识别请求和层粒度的跨 token 复用是否带来可测收益。

### 2.2 常规网络状态复用

RDMA 队列、远程地址注册和连接状态本身具有持久性。拟争取的技术区别应落到专家语义对应关系、真实路由变化触发的更新，以及返回结果和资源释放的协议上。

### 2.3 局部性路由研究

[Oracle-MoE](https://proceedings.mlr.press/v267/zhou25b.html)是已有检索中的局部性路由工作。模型访问局部性与通信控制器的具体更新协议需要分别比较。

## 3. 方案详情

### 3.1 硬件组成

源端包含专家通信记录表、路由比较单元、发送描述符单元和失效处理队列。接收端包含记录标识解析表、共享接收缓冲池、专家执行队列和完成通知单元。

这些模块可部署在智能网卡、片上网络接口、芯粒互连端点或 NPU 通信前端。计算阵列由多请求共享。

### 3.2 通信记录

| 字段 | 用途 |
|---|---|
| 模型版本、请求标识、层号 | 确定记录归属，隔离不同请求 |
| 专家编号及部署版本 | 识别实际专家与所在设备 |
| 目标端点、接收队列标识 | 定位接收端的专家处理入口 |
| 返回端点及输出位置描述 | 将结果交还当前请求 |
| 记录版本、消息序号 | 区分更新前后的在途消息 |
| 缓冲可用额度及在途计数 | 控制流量及安全释放 |

记录描述符可跨 token 保留，但具体接收缓冲槽位按消息动态领取并回收。这样无需为大量请求长期独占物理接收缓冲。

### 3.3 首次建立

真实路由首次选中专家后，源端查询专家部署位置。接收端分配逻辑记录标识并关联专家队列；双方完成版本确认。第一条消息可携带完整描述，与建表合并。

记录有效后，消息只携带接收端可解析的记录标识、版本、序号以及本次激活。量化参数、动态形状或多专家权重等每次变化的字段仍须传递。

### 3.4 连续访问

源端比较当前真实专家与有效记录，检查模型、形状和部署版本。匹配时复用目标和队列描述，在有可用额度时直接发送。接收端依据记录标识入队，完成专家计算后，使用消息序号将输出写入对应返回位置。

返回地址随 token 变化时，可以使用预登记的环形输出空间及序号偏移，或在消息中携带该次偏移。只有稳定字段可以省略。

### 3.5 路由切换与在途正确性

路由变化时，源端创建新版本记录，将后续消息绑定到新版本。旧版本保持有效，直至其在途消息完成。接收端按版本识别处理入口，返回结果按请求、层和序号定位。

旧记录在所有引用结束后回收；超时和设备故障进入常规重试流程。重试须用消息序号检测重复，避免一个专家输出被汇合两次。

普通自回归执行同一请求同一层往往只有很少在途消息；多请求交错、流水化和批量验证场景会提高版本管理的重要性。

### 3.6 迁移、拥塞和多专家扩展

专家迁移时，部署管理方发布新版本并使旧记录失效。目标队列拥塞时，源端等待额度或由运行时选择合法副本并更新记录。无法使用快速记录的消息走完整描述路径。

Top-k 模型可对每个被选专家维护子记录，并保留本次汇合权重。当前项目 Top-1 数据不直接证明 Top-k 的状态命中率。

## 4. 四阶段实施例

1. **产生真实专家。** 设备 A 完成某请求第 12 层 Attention，router 选择设备 B 上的专家 3。
2. **建立或复用通信记录。** 首次访问时登记 B 的专家队列及 A 的返回位置；后续相同选择复用记录，申请本条消息所需缓冲。
3. **传输、计算和返回。** A 发送新激活，B 根据记录进入专家 3 队列，计算后将结果按序号返回 A，释放缓冲额度。
4. **真实切换时更新。** 下一次选择设备 C 上的专家 5，则建立新版本并发送；B 上的旧在途结果仍按旧版本完成，最后回收旧记录。

## 5. 技术效果与模拟方法

### 5.1 优化对象

拟减少的是目标解析、分发描述生成、逐轮控制和稳定元数据传输。激活、专家输出、必要完成通知和拥塞等待仍需计入。

令 $T_{common}$ 为两方案共有的计算、有效载荷传输及其他开销；$T_{dispatch}$ 为优化后基线仍需逐轮执行的可替代分发开销；$T_{check}$ 为记录检查开销；$T_{update}$ 为失效后的更新开销；$p_{invalid}$ 为实际记录失效率：

$$
T_{base}=T_{common}+T_{dispatch},
$$

$$
T_{new}=T_{common}+T_{check}+p_{invalid}T_{update}+T_{extra}.
$$

$T_{extra}$ 包含额外版本管理、状态访问和排队成本。收益条件为新增开销之和低于 $T_{dispatch}$。

### 5.2 示例敏感性分析

下表仅为微秒级假设演算：$T_{common}=20$、$T_{check}=0.2$、$T_{update}=2$、$T_{extra}=0.1$、$p_{invalid}=0.06$。新方案耗时为 20.42 微秒。

| 基线可替代分发开销 | 基线总时延 | 新方案时延变化 |
|---:|---:|---:|
| 0.2 微秒 | 20.2 微秒 | 增加约 1.1% |
| 1 微秒 | 21 微秒 | 降低约 2.8% |
| 3 微秒 | 23 微秒 | 降低约 11.2% |

这说明必须测量优化基线中可省略的具体工作，不能仅根据 6% 的专家切换率推出端到端加速。

### 5.3 状态容量

若 1024 个请求、64 层、每条源端记录 64 字节，则源端完整记录约需 4 MiB。该配置仅为容量示例，接收表、队列及共享描述另计。可将近期记录放在片上 SRAM，其余放在设备内存，统计记录缓存失效的代价。

## 6. 拟保护的技术点

1. **请求与层粒度的专家通信状态。** 将专家身份、接收队列、返回描述和有效版本建立持续对应关系。
2. **真实路由变化驱动的增量更新。** 稳定访问使用简化描述，发生变化时更新对应记录。
3. **双端版本与在途消息关联。** 新旧记录并存至完成，保证返回结果及重试正确归属。
4. **逻辑记录与物理缓冲解耦。** 保留路由关系，同时动态获取接收空间，并在迁移或拥塞时安全回退。

## 7. 专利价值与商业价值

- **系统/装置类价值：** 明确源端与接收端控制器、记录存储和计算队列的组合。
- **方法类价值：** 覆盖建表、连续发送、真实变化更新、结果返回和旧状态回收。
- **架构平台类价值：** 可映射到服务器网卡、多卡互连和芯粒网络。
- **产品价值：** 在小消息 decode 中降低控制开销，为连续路由模型提供专用通信支持。

## 8. 可发现性

### 8.1 公开资料

产品资料、驱动接口或专利文本中可能披露请求层级路由记录、专家队列标识、增量描述与迁移失效机制。

### 8.2 软件与固件痕迹

可观察记录注册、更新、版本发布、在途计数、接收额度和回收命令。固件反汇编或寄存器说明可进一步确认真实专家比较与发送路径的关系。

### 8.3 通信轨迹

相同专家连续访问时，消息中的稳定描述被短标识替代；切换时出现更新消息。双端跟踪可核对旧版本结果在新版本生效后仍被正确接收。

### 8.4 组合证据

以相同有效载荷、不同专家切换率的对照实验，结合消息格式、控制命令和版本行为，识别完整机制。仅观察低延迟或长连接不能证明采用了本方案。

## 9. 可规避性与上位保护建议

### 9.1 潜在可规避点

1. 以远程地址或队列号替代专家号。
2. 将记录放在 GPU 内核、运行时或交换芯片中。
3. 采用全局代际号或等待旧消息全部完成后再切换。
4. 每次仍发送完整头部，但复用端点解析及执行队列。

### 9.2 对应上位保护建议

1. 以能够映射到真实专家执行位置的标识定义状态。
2. 分别描述方法和通信装置实施例，覆盖可行的部署位置。
3. 描述更新前后消息归属与安全回收条件，包含多种实现。
4. 将状态解析复用作为核心，将头部压缩作为从属实施方式。

这些扩展仍需接受已有连接缓存、RDMA 状态管理与专家通信技术的逐项比对。

## 11. 待验证事项与立项判断

第一步用现有通信实现分解 dispatch/combine 时间，确认可省略的控制工作。第二步回放真实连续路由轨迹，测量记录命中、更新与缓冲等待。第三步加入迁移、拥塞和请求交错，验证结果归属正确性。

该方向与三阶段算法关联明确，也适合甲方的互连及控制器能力。独立专利价值主要取决于具体双端协议与相对优化基线的增益，应优先完成小规模通信原型。
