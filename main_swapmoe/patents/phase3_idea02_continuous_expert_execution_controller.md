# 基于真实路由变化的连续专家执行控制器及任务发射方法

## 摘要

本方案在 GPU/NPU 的任务控制侧保留每个请求、每一层的专家执行记录。真实路由与记录一致且权重有效时，控制器复用权重地址、计算描述符和执行流程，仅绑定当前激活地址并发射计算；路由或权重映射变化时更新记录。

三阶段算法降低专家切换需求，使这一快速执行分支成为常见路径。拟优化对象是逐 token 的执行配置与控制开销，主要适用于小批量、短计算任务和低延迟推理。

本文为技术构想，尚无该控制器实测或完整专利新颖性结论。

## 1. 问题动机与算法依据

通用执行流程需要识别专家、取得权重地址、绑定输入输出并提交计算。相邻 token 使用同一专家时，其中一部分配置可以保留。已有 GPU 图执行和持久化内核也能降低这些开销，因此本方案的目标是将真实路由、专家映射有效性与设备侧计算发射进一步连接起来。

Attention-Mean Routing 通过注意力输出的因果局部均值选择专家，同时保持专家输入为完整表征。项目报告中的 M、L 专家切换率为 5.48%、6.40%。这支持大多数相邻访问复用专家身份，但实际执行记录命中率还受请求切换、权重淘汰和模型版本更新影响。

## 2. 现有方案与相关工作

| 基线 | 已有能力 | 需要验证的额外空间 |
|---|---|---|
| 普通算子提交 | 动态配置、灵活执行 | 重复提交及配置开销 |
| CUDA Graph 或同类图执行 | 复用执行图，降低提交成本 | 路由与权重地址变化能否由设备直接安全处理 |
| 持久化内核 | 常驻设备，循环处理任务 | 专家状态查询及配置复用是否仍消耗可观资源 |
| 专家执行硬件选择 | 按专家请求和设备状态选择执行设备 | 连续访问下局部执行配置的有效性与发射控制 |

AMD US11893502B2 是已有检索中的专家执行硬件选择线索，应进一步比较其调度状态与本方案状态的关系。立项基线应包含图执行或持久化实现。

## 3. 方案详情

### 3.1 控制器结构

控制器包含执行记录表、真实专家比较器、映射版本检查器、任务描述符存储及发射队列。执行记录以模型、请求、层号为索引，记录专家号、权重槽位、权重版本、算子形状及完成状态。

输入输出地址随 token 更新；记录中的权重地址只有在版本有效且槽位未被替换时才可复用。

### 3.2 快速执行路径

router 输出当前真实专家号后，控制器检查专家号、形状、模型版本和权重槽位版本。全部匹配时，绑定当前激活地址和输出位置，向共享计算阵列提交预存描述符。

每个 token 仍执行完整专家计算。保留的是控制配置和地址映射，不包含复用上一个 token 的计算结果。

### 3.3 更新路径

专家变化时，控制器查询当前驻留表。若权重已在设备中，直接重绑定；否则等待加载完成。新记录在权重可用后发布，旧记录的在途任务结束后才允许覆盖相关槽位。

形状变化、量化格式变化、模型更新及抢占均触发版本失效。共享记录可按专家索引保存不变部分，请求记录只保存引用，控制片上状态容量。

### 3.4 软件接口与实现形态

驱动在模型加载时登记专家布局、计算描述符和合法地址范围。运行时提交当前 token 的激活位置、请求和层号。硬件完成匹配、绑定及发射；缺失或异常通过完成队列反馈。

可先以 FPGA 控制队列或 NPU 固件原型验证，再决定是否制作专用逻辑。若软件实现已消除绝大部分开销，硬件专用化的收益需要重新评估。

## 4. 四阶段实施例

1. **Attention 与路由完成。** 设备得到当前完整激活和真实专家号。
2. **检查执行记录。** 与上一轮相同且权重版本有效时，绑定本次输入输出。
3. **发射计算。** 共享阵列执行专家并返回结果；未匹配时，先解析新专家地址和完成必要加载，再执行。
4. **保留配置。** 完成状态推进，记录继续服务下一 token；请求结束时释放请求级状态。

## 5. 时延和资源模型

设每次完整配置耗时 $T_{setup}$，匹配检查与地址绑定耗时 $T_{check}$，记录失配概率为 $p$，相同计算及数据传输耗时为 $T_{body}$：

$$
T_{base}=T_{body}+T_{setup},
$$

$$
T_{new}=T_{body}+T_{check}+pT_{setup}.
$$

收益条件为 $T_{check}<(1-p)T_{setup}$。示例假设 $T_{body}=20$ 微秒、$T_{setup}=2$ 微秒、$T_{check}=0.2$ 微秒、$p=0.06$，则时延从 22 微秒降至 20.32 微秒，降低约 7.6%。这些数值仅演示模型，并非设备测量。

若优化基线的配置仅需 0.2 微秒，本方案可能没有收益。因此首要测量对象是已有图执行或持久化内核中的剩余控制开销。

表容量为 $N_{request}N_{layer}S_{entry}$。应统计命中率随表容量及请求数的变化，避免专家切换少但状态表频繁被淘汰。

## 6. 拟保护的技术点

1. **以请求和层组织的专家执行记录。** 同时保存专家身份、权重有效性和计算描述符引用。
2. **真实路由驱动的设备侧条件发射。** 匹配时复用配置并绑定当前激活，失配时执行更新流程。
3. **执行记录与权重槽位的版本联动。** 防止地址复用后调用错误专家权重。
4. **共享阵列下的多请求状态管理。** 在任务交错、抢占和恢复时保持各请求记录正确。

## 7. 专利价值与商业价值

- **系统/装置类价值：** 专用比较、版本检查和描述符发射逻辑可集成到 NPU 控制前端。
- **方法类价值：** 完整描述从真实路由到匹配发射、更新和安全失效的流程。
- **架构平台类价值：** 可适配不同专家算子及权重存储介质。
- **产品价值：** 以较小控制逻辑改善小批量推理延迟，并减少控制核心参与。

## 8. 可发现性

驱动或固件中可能出现专家描述符注册、执行记录容量、版本更新和快速发射计数器。寄存器与命令队列可显示激活地址每次更新而权重描述符连续复用。

黑盒可固定计算形状并改变真实专家切换率，测量任务发射延迟与配置流量。要结合接口证据区分一般图复用和本方案的路由状态联动。

## 9. 可规避性与上位保护建议

### 9.1 潜在可规避点

1. 在持久化内核内部完成比较和描述符复用。
2. 用专家地址而非专家编号判断是否变化。
3. 用代际号、间接指针或硬件一致性机制保证有效性。
4. 将记录按专家共享，避免逐请求保存完整描述符。

### 9.2 对应上位保护建议

1. 描述设备侧条件发射方法，硬件控制器作为具体装置实施方式。
2. 覆盖能唯一关联实际专家的身份或地址标识。
3. 覆盖计算描述与权重映射的一致性验证关系。
4. 覆盖请求记录引用共享描述的组织方式。

此处是拟扩展的保护范围，不能据此判断竞争实现是否落入授权权利要求。
